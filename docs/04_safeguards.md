# 04 · 防呆機制

> 本文件說明系統的攔阻設計：六層防呆、異常分類法，以及針對新進人員的防誤觸設計。
> 資料來源與降級見 [`03_data_sources.md`](03_data_sources.md)。

---

## 1. 設計前提：假設操作者會累、會被打斷、會是新人

災害應變的作業條件是**深夜、輪班、每 3 小時一報、隨時被電話與詢問打斷**。
在這種條件下，「要求操作者更仔細」不是可行的機制設計。

因此防呆的設計目標不是「防止錯誤發生」，而是：

> **讓錯誤在造成後果之前被攔下，而且攔阻理由要能說得出來。**

「說得出來」是為什麼安全檢查**全部使用確定性規則、不使用 LLM**——
攔阻必須可重現、可稽核、可解釋。副作用是 LLM 服務中斷時，安全機制完全不受影響。

## 2. 六層防呆

資料從進入到產出，依序通過六道獨立的檢查層。任一層都可能攔停。

### 第一層：輸入結構驗證

以 schema 對每筆證據做強制驗證，不符即拒絕：

| 檢查 | 規則 |
|---|---|
| 證據編號格式 | 正規表示式強制 `EVD-YYYYMMDD-{來源}-NNN` |
| 來源分類 | 白名單列舉，不接受未定義來源 |
| 雜湊值 | 長度固定 64 字元 |
| 摘要長度 | 上限 200 字 |
| **時間順序** | `observation_time ≤ collection_time`，違反即為 E003 |
| **雨量範圍** | 10 分鐘雨量必須落在 0–300mm |

### 第二層：時序與物理極限

| 檢查 | 觸發 | 嚴重度 |
|---|---|---|
| 上游連續 3 次取數失敗 | E001 | P1 |
| 欄位格式錯誤 | E002 | P2 |
| 時間倒置 | E003 | P2 |
| 物理極限違反 | E005 | P1 |
| **滑動視窗斜率異常**（跨報次變化率） | E005 | P1 |
| **上游結構漂移**（欄位新增／改名／消失） | E007 | P2／P3 |
| 代理推論逾時 | E004 | P3 |
| 主備自動切換 | E001 | P2 |

### 第三層：輸出規範（Format Gate）

在**生成之前**驗證輸入完備，在**生成之後**驗證輸出合規：

| 檢查 | 說明 |
|---|---|
| 禁用詞比對 | 規則庫收錄約 50 條，分為規格／量詞／量級／時態／判斷等類別 |
| 語音轉寫錯詞修正 | 收錄 32 組常見同音誤植，自動取代 |
| 報告類型分流 | 不同文件類型套用不同規則子集，避免誤殺 |
| 必填章節缺漏 | 章節清單比對，缺漏即拒絕 |
| 引用標註存在性 | 正文必須含證據標記，無標註即拒絕 |

> 規則庫是**可維護的資料檔**，不是寫死在程式裡。新發現的錯誤樣態由業務人員增補，
> 不需要改程式。這是讓「經驗」能夠累積成「機制」的關鍵設計。

### 第四層：評分閾值（Agent B）

| 維度 | 權重 | 單項門檻 |
|---|---:|---:|
| 數據準確度 | 40% | 0.70 |
| 資料覆蓋完整度 | 25% | 0.65 |
| 語氣符合度 | 20% | 0.60 |
| 邏輯連貫性 | 15% | 0.60 |

**加權總分門檻 0.85，且四項單項門檻須同時滿足；重試上限 3 次。**

### 第五層：人工介入（A6）

| 機制 | 說明 |
|---|---|
| Hard Gate 中斷 | 重大異常時凍結流程等待裁決 |
| 評分退回中斷 | 任一閾值不通過即退回或轉人工 |
| 角色權限分離 | 建立工作階段與提交決策**分屬不同角色** |
| 終端狀態保護 | 已完成／已失敗的執行緒拒絕重複續跑 |
| 持久化檢查點 | 中途失效可原地恢復，不會遺失狀態 |

### 第六層：採集端保護

對外部來源採取速率限制與退避重試，避免自身成為上游系統的負擔——
災害期間上游系統本來就在承受高流量。

## 3. 異常分類法

異常以三個維度描述，目的是讓**修復的人立刻知道該找誰**。

### 3.1 四大類：誰該修

| 類別 | 範疇 | 排查起點 |
|---|---|---|
| **A · 來源** | 上游連線、格式、結構變動 | 資料提供方或介接設定 |
| **B · 資料** | 數值本身不合理、時序矛盾、來源衝突 | 資料內容與登打 |
| **C · 流程** | 逾時、執行失敗 | 系統維運 |
| **D · 輸出** | 用詞、格式、規則違反 | 報告內容與規則庫 |

### 3.2 錯誤碼

| 碼 | 意義 | 類別 | 嚴重度 |
|---|---|:---:|---|
| `E001` | 資料來源連線失敗 | A | P1／P2 |
| `E002` | 欄位格式錯誤或結構改變 | A | P2 |
| `E003` | 時間排序異常 | B | P2 |
| `E004` | 代理推論逾時 | C | P3 |
| `E005` | 物理極限違反／變化率異常 | B | P1 |
| `E006` | 規則庫違規 | D | P2／P3 |
| `E007` | 上游結構漂移（schema drift） | A | P2／P3 |
| `E008` | **雙來源數值衝突** | B | P2 |

### 3.3 嚴重度：對應什麼行為

| 級 | 行為 | 能否由操作員解鎖 |
|---|---|---|
| **P1** | **禁止生成**，流程必須暫停；通常需啟動備援作業程序 | 否，需走人工備援流程 |
| **P2** | **需人工確認**，流程暫停，確認後可解鎖續行 | 是 |
| **P3** | **標記續行**，不阻擋，但於報告加註警語 | 不需要 |
| **P4** | **僅記錄**，不影響流程也不出現在報告，供事後稽核 | 不需要 |

> **實作現況的誠實說明**：目前 P1 與 P2 在程式中走相同的中斷與解鎖路徑，
> 尚未細分出「P1 必須強制走備援程序」的差異行為。這是已知待補項目，
> 不是設計上認為兩者相同。

### 3.4 一筆資料可以同時觸發多類異常

這是設計允許的。例如同一筆證據可能同時有格式錯誤（E002／A 類／P2）、
時間倒置（E003／B 類／P2）與雨量超出物理極限（E005／B 類／P1），
三者分別記錄，最終以最高嚴重度決定流程行為。

### 3.5 雙來源衝突（E008）的特殊處理

當結構化欄位與承辦人自由文字描述的數值不一致時：

- **不自動選邊**。系統不判斷哪個對。
- 兩個數值**並陳於正文**，附上系統建議與判斷理由。
- 高敏感主題（撤離、收容、傷亡、受災戶）**強制標記需人工確認**。
- 衝突事件落帳，保留雙值與理由。

**這是整套系統最重要的一條原則：資料衝突時，系統的職責是把矛盾攤開給人看，
不是替人做決定。**

## 4. 新進人員防誤觸設計

防呆的驗收標準是「新進人員在最差條件下操作，也不會造成災難性後果」。
以下是逐一對應的風險情境：

| 風險情境 | 對應防呆 |
|---|---|
| 直接核准有重大異常的報告 | 核准權限限定特定角色；P1／P2 異常預設展開並高亮 |
| 忘記檢查資料時間 | 報告自動帶入觀測時間、採集時間與延遲分鐘數；超過門檻自動加警語 |
| **誤將內部草稿對外發布** | 介面上**沒有「對外發布」按鈕**，只有儲存與送出；對外發布為系統外流程 |
| 修改時改錯數字 | 全程記錄修改前後差異，可回溯 |
| 重複建立工作階段 | 以執行識別碼為鍵，重複建立不會產生第二筆 |
| 對已完成的流程重複送出 | 終端狀態保護，直接回絕 |
| 不知道哪些欄位必填 | schema 強制驗證＋章節缺漏由閘門攔截 |
| 用錯應變等級導致頻率錯誤 | 未指定等級時採**保守預設**（較長間隔） |
| 誤觸結報 | 結報**永遠需要人工確認**，不可自動結報 |
| 漏看異常分類 | 介面依四大類顯示，並預設展開高嚴重度項目 |
| 送出過程中系統失效 | 檢查點保留中途狀態，事後可恢復 |

> 「介面上沒有對外發布按鈕」是刻意的設計，而非功能未做。
> **系統能力邊界本身就是一種防呆**——做不到的事，就不會被誤觸。
