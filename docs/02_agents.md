# 02 · 代理規格

> 本文件逐一說明九個元件。工作流拓撲與狀態設計見 [`01_architecture.md`](01_architecture.md)。

## 總覽

| 代理 | 職責 | 生成式 AI | 失效時的行為 |
|---|---|:---:|---|
| A1 氣象資料代理 | 取得雨量、風速 | ❌ | 改用已存備份並標示資料時間 |
| A2 災情看板代理 | 取得災情、災點、出動人車等 | ❌ | 記錄採集失敗（E001），交由 A3 判定 |
| A3 異常審核代理 | 六類異常偵測與嚴重度分級 | ❌ | 本身失效即視為不可信，攔停 |
| Hard Gate | 重大異常時中斷等待人工裁決 | ❌ | — |
| A4 脈絡管理代理 | 狀態向量更新、跨報差異、證據嵌入 | ⚠️ 嵌入 | 嵌入失效則降級為關鍵字檢索 |
| Format Gate | 起草前的格式與時間範圍驗證 | ❌ | FAIL 一律導向 Hard Gate |
| A5 起草代理 | 將結構化資料寫成報告敘述 | ✅ | 退回官方制式敘述並標示降級 |
| Agent B | 草稿品質四維度評分 | ✅ | 標記 degraded，直接送人工 |
| A6 人工協調代理 | 承接人工決策並套用 | ❌ | — |

## A1 · 氣象資料代理

| 項目 | 內容 |
|---|---|
| **職責** | 自中央氣象署開放資料取得雨量與風速，標準化觀測時間，計算原始回應雜湊 |
| **輸入** | 執行中繼（`run_id`、`trigger_type`） |
| **輸出** | `raw_evidence`（累加）、`active_errors`（累加） |
| **生成式 AI** | 否 |

**設計重點**

- 每筆證據同時記錄 `observation_time` 與 `collection_time`，並對原始回應計算 SHA-256。
- 取數失敗時不讓流程崩潰，而是啟動降級：改用先前存下的觀測值，
  並在報告中標示「此為備份資料，資料時間為 ⋯」。前端以綠／黃標籤區分即時與備份。
- 降級決策全數寫入 `degradation_report`，可統計降級啟動率。

**已知限制**：氣象開放資料 API 僅回傳即時值，歷史值需另行封存累積。

---

## A2 · 災情看板代理

| 項目 | 內容 |
|---|---|
| **職責** | 自災情看板資料庫唯讀取得災情統計、災點、收容、出動人車等欄位 |
| **輸入** | 執行中繼 |
| **輸出** | `raw_evidence`（累加）、`active_errors`（累加） |
| **生成式 AI** | 否 |

**設計重點**

- **唯讀直連**。系統對來源資料庫僅有查詢權限，不具寫入能力——這是架構層級的保證，
  不是靠程式自律。
- 資料庫共 41 張表，產報實際直接取用 20 張。
- 內建 **schema drift 偵測**：來源結構變動（欄位新增／改名／消失）會被偵測並摘要，
  而不是讓解析靜默地取到空值。這是長期維運中最容易出事、也最容易被忽略的一類故障。
- 單一欄位無資料時，可依設定啟用 **EMIC 備援**：以中央系統的縣級合計數字補位，
  並在報告中標註來源，同時發出警報提醒承辦人回源頭補填。
  **備援僅適用於指定欄位，且為唯讀取用，系統不寫入 EMIC。**

## A3 · 異常審核代理

| 項目 | 內容 |
|---|---|
| **職責** | 對 A1／A2 產出的所有證據執行規則式異常偵測與嚴重度分級 |
| **輸入** | `raw_evidence`、`previous_d_state` |
| **輸出** | `active_errors`（累加）、`hard_gate_triggered` |
| **生成式 AI** | 否 |

### 異常分類

異常以三個維度描述：**錯誤碼 × 嚴重度 × 類別**。

| 錯誤碼 | 意義 | 典型觸發 |
|---|---|---|
| `E001` | 採集為空 | 應有資料的來源回傳空集合 |
| `E002` | 格式錯誤 | 證據編號、雜湊值格式不符規範 |
| `E003` | 時間排序異常 | 觀測時間晚於採集時間 |
| `E004` | 逾時 | 上游來源未在期限內回應 |
| `E005` | 物理極限違反 | 數值超出物理可能範圍或變化率異常 |
| `E006` | 規則庫違規 | 內容命中禁用詞或已知錯詞 |

| 嚴重度 | 處置 |
|---|---|
| **P1** | 攔停，觸發 Hard Gate |
| **P2** | 攔停，觸發 Hard Gate |
| P3 | 標記後續行 |
| P4 | 標記後續行 |

類別維度沿用輔導期間確立的四大分類：A 來源／B 資料／C 流程／D 輸出，
用於統計異常集中在哪個環節。

### 兩個值得一提的檢查

**物理極限（E005）** — 例如 10 分鐘雨量超過 300mm 即判定為不可能值。
這類錯誤通常源於單位標示錯誤或資料串接錯位，人眼在高壓下極難察覺。

**滑動視窗斜率監控（E005）** — 讀取上一報的狀態向量，計算 Δ 雨量 / Δ 時間，
變化率超過 50mm/hr 即觸發。這道檢查抓的是**跨報次**的異常，
單看任何一份報告都看不出來。

### 設計原則

A3 只回傳**本次新增**的錯誤，上游 A1／A2 已記錄的錯誤由狀態 reducer 自動累加，
不重複計算也不覆蓋。

## Hard Gate · 人工裁決中斷點

| 項目 | 內容 |
|---|---|
| **職責** | 在重大異常或格式驗證失敗時凍結流程，等待人工裁決 |
| **觸發來源** | A3（`hard_gate_triggered`）、Format Gate（`format_gate_passed = false`） |
| **裁決選項** | `approved`（續跑至 A4）／`rejected`（終止） |
| **生成式 AI** | 否 |

實作為 LangGraph `interrupt()`，狀態寫入 checkpoint 後凍結，
可跨程序重啟、跨小時等待。`approved` 時將異常標記為已解決而非刪除，保留稽核軌跡。

---

## A4 · 脈絡管理代理

| 項目 | 內容 |
|---|---|
| **職責** | 更新狀態向量、產製跨報差異、將證據嵌入供檢索 |
| **輸入** | `raw_evidence`、`previous_d_state` |
| **輸出** | `d_state_vector`、`diff_log`（累加）、`evidence_chunks`、`degradation_report` |
| **生成式 AI** | 否（使用嵌入模型，非生成模型） |

**D-State Vector** 是本報次的結構化狀態快照（雨量、風速、停電戶數、撤離收容人數、
對應時間）。與上一報的向量相比即得 **Diff Log**——這是跨報一致性檢查的基礎，
也是「累計值不得下降」這類規則的實作依據。

證據嵌入採 sentence-transformers，供 A5 起草時檢索相關脈絡。
嵌入失效時降級為關鍵字檢索，流程不中斷。

---

## Format Gate · 格式驗證閘門

| 項目 | 內容 |
|---|---|
| **職責** | 起草前驗證證據的必填欄位與時間範圍 |
| **輸入** | `evidence_chunks` |
| **輸出** | `format_gate_passed`、`format_gate_failures`、`format_gate_verdict`（PASS / FAIL） |
| **生成式 AI** | 否 |

必填欄位：`evidence_id`、`source_type`、`observation_time`、`content_summary`。

**為什麼放在生成之前**：讓 LLM 拿著缺欄位的資料去寫，產出的會是看似完整、
實則缺漏的報告——這比直接失敗更危險。閘門在生成前擋下，
FAIL 一律導向 Hard Gate 交人處理，不自動放行。

---

## A5 · 起草代理

| 項目 | 內容 |
|---|---|
| **職責** | 將狀態向量、差異紀錄與檢索到的證據寫成報告敘述 |
| **輸入** | `d_state_vector`、`diff_log`、`evidence_chunks`、`event_name` |
| **輸出** | `draft_report` |
| **生成式 AI** | ✅ 是（本地端 Ollama） |

**約束條件**

- System prompt 強制嵌入報告章節結構（壹～柒章）與引用規則。
- 正文內嵌 `[EVD-xxx]` 來源標記，文末自動生成參考來源清單。
- **數值不由 LLM 產生**。數值來自 A1／A2 的結構化通道，
  LLM 的工作是把它們組織成通順敘述。

**失效行為**：LLM 服務不可用時，`draft_report` 的開場白退回官方制式敘述，
並將 `opening_source` 標記為 `fallback`，前端顯示降級提示。
**流程不中斷，報告仍然產出**——只是文句較制式。

## Agent B · 品質評分

| 項目 | 內容 |
|---|---|
| **職責** | 對草稿進行四維度評分，決定通過、退回重寫或轉人工 |
| **輸入** | `draft_report`、`evidence_chunks` |
| **輸出** | `scorecard`、`retry_count`、`human_review_required` |
| **生成式 AI** | ✅ 是（RAGAS + LLM-as-judge） |

### 評分維度與權重

| 維度 | 意義 | 權重 | 單項門檻 |
|---|---|---:|---:|
| `faithfulness` | 數據準確度 | 40% | 0.70 |
| `context_recall` | 資料覆蓋完整度 | 25% | 0.65 |
| `answer_relevancy` | 語氣符合度 | 20% | 0.60 |
| `coherence` | 邏輯連貫性 | 15% | 0.60 |

**加權總分門檻 0.85，且四個單項門檻必須同時滿足。**

### 為什麼要有單項門檻

只看加權平均會有盲點：某一維度嚴重不足時，可能被其他維度的高分掩蓋而蒙混過關。
加上單項門檻後，**任一維度低於下限即不通過，無論總分多高**。

### 退回與退場

```
分數不足 且 retry_count < 3  →  退回 A5 重寫，retry_count += 1
分數不足 且 retry_count >= 3 →  停止重寫，強制轉人工介入
```

上限存在的理由：模型能力不足時無限重試只是浪費時間，
**明確退場並交給人，比一直重試更誠實。**

### 反諂媚設計

評分標準以雜湊值凍結（`frozen_rubric_hash`），跨重評輪次比對，
避免評分基準在重試過程中漂移。分數軌跡（`score_trajectory`）為 append-only，
可觀察多輪重寫是否真的改善，或只是評分寬鬆化。

**失效行為**：評分服務不可用時標記為 degraded，草稿直接送人工審核——
**不會因為「評不了分」就自動放行。**

## A6 · 人工協調代理

| 項目 | 內容 |
|---|---|
| **職責** | 承接承辦人決策並套用至最終報告 |
| **輸入** | `draft_report`、人工決策 |
| **輸出** | `human_decision`、`human_modified_report`、`final_report_internal`、`final_report_external`、`report_time` |
| **生成式 AI** | 否 |

**三種決策**：`approved`（採用）／`modified`（修改後採用）／`rejected`（退回）。

**修改入帳**：承辦人的修改以差異（diff）形式寫入帳本，記錄修改前後、修改人、
時間、原因分類與依據。寫入前先套用去識別化，避免帳本本身成為個資外洩管道。

**修改紀錄不用於自動學習。** 帳本的用途是稽核與統計（人工修改率是可觀測指標之一），
不會回頭自動調整模型行為——避免錯誤案例污染後續產出，也避免系統行為在無人察覺下漂移。

**角色權限**

| 角色 | 權限 |
|---|---|
| editor | 建立審核工作階段、啟動工作流；**不可提交最終決策** |
| reviewer | 檢視工作階段、提交審核決策 |
| admin | 同 reviewer，另含使用者管理 |

**簽核與對外發布由人於系統外執行。** 系統的終點是產出經確認的報告，
不具備任何自動對外發送能力。
